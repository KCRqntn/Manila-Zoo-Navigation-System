# Changes, 28 October 2026: companions on every visit

## Visitor form
- After the visitor's own details (first visit) or after logging in (returning visitor, no account form),
  the form asks **"Are you visiting alone today, or with companions?"** (Just me / With companions) and,
  with companions, **"How many people are accompanying you today?"** (− / + buttons).
- **Your Companions Today:** the visitor is shown as "You: age 35 · Adult (registered visitor)"; the
  age-group counts (children, adults, senior citizens) and ages are for companions only. The form checks
  that the companions listed match the number given and shows "Total group size: 4 (you + 3 companions)".
- PWD is chosen from the people listed (the visitor or a companion), so nobody is counted twice.
- Review step: "Companions" and "Total group size"; "You + 3 companions = 4 people".

## Database
No schema change was needed. The existing tables already hold it:
- `visitor_profiles`: one row per registered visitor (account id = Supabase user id). Never duplicated.
- `visitor_registrations`: one row per visit (visit id, visitor id, visit number, date and time,
  group size). Companions = group size − 1.
- `visitor_group_members`: one row per person on that visit (age, category, PWD flag, whether it is the
  registered visitor). A database check at commit makes the people add up to the group size, and the
  server requires exactly one registered visitor per visit.

## Admin dashboard (Visitor Registrations and Dashboard)
- Registered visitor accounts · Visits (visit transactions) · Total attendance (visitors + companions) ·
  Attendance today.
- New: First-time visits · Returning visits · Companions (total) · Average group size.
- Children, adults, senior citizens, PWD visitors (unchanged).
- Daily, **weekly** (new, from Monday) and monthly attendance charts.
- Visit records table and CSV export: new **Companions** column next to **Group size**.

## Login, sign-up and password visibility (same day)
- **QR code → Login form.** The website QR code (unchanged address: `/visitor-registration`) now always opens
  **Visitor Login**. "Don't have an account? **Sign up**" opens the complete registration form

  The "First visit / I've visited before" tabs and the "this phone has an account" memory were removed.

## Sessions, admin link, linked companions, counting and rewards (same day, evening)
**Causes found**
- Logins were already kept on the phone (Supabase saves the session in the browser). They seemed lost because
  (1) the phone link changes when the laptop restarts: a new address is a different site for the phone, with
  no saved login; this goes away once the system is hosted on a fixed domain; and (2) until earlier today the QR
  page opened on "First visit" unless the phone remembered an account.
- The "Administrator login" button was in the welcome window shown on visitor pages.
- Companions couldn't be matched to their own accounts, so two friends registering each other were counted twice.
- Game points didn't depend on a registered visit.

**Changes**
- Session policy (`contexts/AuthContext.tsx`): the login stays across tab closing, refresh, rescanning and browser
  restarts; idle limit 30 days for visitors and 12 hours for staff (on that device); an expired or revoked login
  shows "Your session has ended…" with the last email filled in (never the password). Logging out ends the
  session on the server. Visitor logins now go through `/api/auth/login` (audited, slowed after 5 failures).
- Admin link removed from visitor pages. Visitor "Login" buttons open the Visitor Login. Staff sign in at
  `/login` (not linked). Admin pages and every admin API stay protected by role on the server.
- Visitor ID (`MZV-XXXXXX`) for every account, shown after logging in. A companion with their own account can be
  linked by their email + Visitor ID; companions without accounts (babies, children, seniors without a phone)
  need only an age and are saved as people on that visit.
- One count per person per visit day: a database unique index on (account, visit date) over everyone on every
  visit. A second visit by the same account that day, or listing someone already counted, gets a clear message
  and nothing is saved. Works for simultaneous requests too.
- Rewards: game points only when the account is counted in a visit registered today; each points row records
  that visit; still once per game/account/animal.
- Audit log: account created, profile created/updated, visit created, companion linked, duplicate attempts,
  points awarded (plus logins/logouts as before).
- Dashboard: yearly attendance.

**Database migration** `2026-10-28-01-visit-attendance` (applied automatically at API start): `visitor_profiles.visitor_code`,
`visitor_group_members.user_id` + `visit_date`, unique index `visitor_group_members_one_per_day`, two triggers
that keep each person's date and the registered visitor's account in step with their visit, and
`game_progress.registration_id`. Existing data: one real account already had two visits today; only the first is
linked (the second is kept and still counted).

**Tested:** 49/49 (14 scenarios), 8/8 linking on screen, 32/32 login flow, 23/23 companions.
